# Citation Number Checks

`knowledgebase/rag/citations.py` provides `validate_citations(answer, sources)`.
It checks whether the bracketed numbers in a generated answer correspond to the
`source_id` values in that answer's retrieved sources. No model call is needed.

## Result

The function returns a `CitationCheck` snapshot:

| Field | Meaning |
| --- | --- |
| `valid_source_ids` | Cited numbers that exist in the supplied sources |
| `invalid_source_ids` | Cited numbers that do not exist in those sources |
| `no_citations` | No recognized `[n]` references appeared in the answer |

Each list contains unique IDs in order of first appearance. Matching uses actual
source IDs, not list positions or filenames. For sources numbered 1 and 3, `[2]`
is invalid even though two sources were retrieved. Checks apply to the current
answer only; numbers from another answer do not establish a match.

The parser recognizes `[n]` with ASCII digits, as requested by the generation
prompt. Adjacent references such as `[1][2]` are supported. Grouped or ranged forms
such as `[1, 2]` and `[1-3]` are not expanded. Leading zeros are interpreted
numerically, and `[0]` is invalid against the service's one-based source IDs.
This is a text-pattern check, not a Markdown parser: a `[1]` inside a quoted
example or code snippet is still recognized.

## Integration and boundaries

After generation, `answer_question` attaches the result as the required
`ChatAnswer.citation_check` field. `answer_in_conversation` carries the same result
into `ConversationAnswer`. The CLI displays the valid/invalid IDs, or states that
no numbered citations were found.

The original answer is never rewritten, rejected, or regenerated by this check.
An answer with invalid references still returns normally and its original text
is saved in conversation history. The check result is returned to callers; it is
not a separate message database field. Callers constructing a `ChatAnswer` directly
must also supply its `CitationCheck`.

A valid number means only that an excerpt can be located. It does not establish
that the excerpt supports the claim, that all claims have citations, or that the
answer is correct. Likewise, no citations is not automatically a failure: a plain
insufficient-evidence response may need none. Human or LLM evaluation assesses
whether evidence actually supports the answer.

## Evaluation records

New runs retain the check under `citation_check` in `answers.jsonl` and each report's
answer snapshot. Markdown reports show the lists for each question. Summaries count
recorded checks, answers with invalid IDs, and answers without numbered citations.
The last two counts use only answers with recorded checks; missing older checks
are not treated as valid or invalid results.

Existing answer records are not modified or regraded. Reports display "Not recorded"
for legacy answers without this field. These diagnostics do not change the semantic
grading rubric or automatically assign a pass/fail score.

## Verification

`make test` covers actual source-ID matching, duplicates, absent citations,
unsupported syntax, per-answer scope, unchanged answer persistence, CLI output,
and evaluation recording with legacy results. These checks are deterministic and
do not require live model access.
