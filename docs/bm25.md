# BM25 Search

Status: the `v2` implementation delegates lexical scoring to
[BM25S](https://github.com/xhluca/bm25s), pinned to `0.3.11`, and is connected to
the default [hybrid retrieval service](hybrid-retrieval.md). It runs locally and
requires no provider request; the hybrid route also embeds the query for vector search.

## Input and Output

`search_bm25(question, chunks, top_k=5, *, k1=1.2, b=0.75)` in
[`knowledgebase/rag/bm25.py`](../knowledgebase/rag/bm25.py) takes a question and a
sequence of canonical chunks. New data supplies `ChildChunk` objects; legacy
`Chunk` and flat `StructuredChunk` objects are also accepted. The caller supplies
unique IDs and filters to eligible files **before** calling the function.

The result is an ordered list of `BM25Match` snapshots:

```python
from knowledgebase.rag.bm25 import search_bm25

# children is a list of eligible ChildChunk snapshots.
matches = search_bm25("minimum GPA 3.0", children, top_k=5)
for match in matches:
    print(match.chunk_id, match.score, match.rank)
```

`chunk_id` always identifies the input retrieval unit, not its parent. Higher
scores rank first; ties use ascending chunk ID. Ranks start at one and are
contiguous after the top-k limit. Only chunks with at least one matching term are
returned, so fewer than top-k results is normal. Empty queries, punctuation-only
queries, empty corpora, and queries with no matching terms return `[]`.

Scores are corpus-dependent lexical relevance values. They are neither cosine
distances nor correctness probabilities. RRF combines route ranks rather than
adding raw BM25 scores to vector distances.

## Tokenization

`tokenize(text)` is shared by questions and chunk text:

| Input | Terms |
| --- | --- |
| `GPA` | `gpa` |
| `DS-GA 1002`, `DS GA 1002`, `DS–GA–1002` | `ds`, `ga`, `1002` |
| `ANTHROPIC_API_KEY` | `anthropic`, `api`, `key` |
| `client.messages.create()` | `client`, `messages`, `create` |
| `3.0` | `3.0` |
| `66%` | `66` |

Unicode case folding normalizes case. Punctuation and underscores split terms;
decimal numbers remain whole. Source text, offsets, and metadata are never
modified. This is word tokenization for matching, separate from tiktoken's token
counts for chunk sizes and evidence budgets.

There is no stemming, stop-word removal, phrase matching, synonym expansion, or
query rewriting. Repeated query terms count once. Hyphenated identifiers match
their spaced forms, but this does not implement arbitrary identifier aliases.
These explicit limits avoid silently making semantic decisions in a lexical scorer.

## Scoring and Lifecycle

For each distinct query term `t` present in chunk `d`, the scorer adds:

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
contribution = idf(t) * tf(t,d) * (k1 + 1)
               / (tf(t,d) + k1 * (1 - b + b * length(d) / average_length))
```

`N` counts nonempty tokenized chunks, `df` counts chunks containing the term, and
`tf` counts term occurrences in one chunk. Punctuation-only chunks are omitted
from corpus statistics. The positive IDF convention and default parameters follow
the [Apache Lucene BM25 documentation](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html).
The formula here includes the conventional `(k1 + 1)` numerator factor; it is not
a claim of score-level equivalence to a Lucene index.

`k1` controls diminishing returns from repeated terms; `b` controls length
normalization. `k1` must be finite and nonnegative, `b` must be between zero and
one, and `top_k` must be positive. Defaults are centralized in
[`config.py`](../knowledgebase/config.py). They are keyword arguments for this
standalone function; the service passes `BM25_K1` and `BM25_B` from `.env`.

BM25S owns corpus statistics and scoring. The adapter selects `method="atire"`,
`idf_method="lucene"` and `dtype="float64"` to retain the formula above. It keeps
the project's identifier/decimal tokenization, unique query terms, nonmatch
filtering and deterministic chunk-ID tie breaking. No stemming or library-default
stopword removal is introduced. BM25S adds only its existing NumPy dependency.

The adapter builds an in-memory index from eligible chunks on each call.
Supplying a changed corpus on the next call
automatically changes the scores and removes absent chunks from consideration.
There is no cached index, database session, file mutation, or model client here.
Repeated full-corpus tokenization is a known cost; performance has not been
benchmarked for large libraries. The service loads only Ready-file children (or
legacy flat chunks) from SQLite on each query. Uploads, deletions, and restarts
therefore need no separate lexical-index rebuild.

The [replacement comparison](../evals/check-runs/20261001-code-consolidation/bm25-comparison.md)
uses the same frozen 25 questions, 16 documents and 64 children on both sides.
All top-20 rankings and measured retrieval metrics match; score differences are
at most `7.11e-15`. Mean local index-and-search time was 2.976 ms before and
5.150 ms after. This is a maintenance simplification, not a measured speedup.

## Verification and Limits

Run `uv run --locked python -m pytest tests/test_bm25.py` or `make test`.
Tests cover hand-calculated scores, rare-term weighting, length normalization,
deterministic ties, common terms in a one-document corpus, identifier and numeric
tokenization, no-match behavior, changed input corpora, exact child identities,
unmodified source metadata, and grounded queries against the frozen NYU FAQ.

The [92-child offline smoke check](../evals/analyses/2026-09-23-bm25-standalone.md)
records results for existing GPA, CPT, course-number, and API-key examples. This
checks the new route in isolation. It does not establish improved answer quality
or resolve the previously observed parent-budget exclusion.
